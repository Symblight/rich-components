# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository

`rich-components` is a pnpm workspace (`packages/*`) of framework-agnostic rich
UI web components built with [Lit](https://lit.dev), published individually to
npm under `@symblight/*`:

- **`packages/data-grid`** (`@symblight/data-grid`) — virtualized MD3 data
  grid: sortable/resizable/paginated columns, row selection, master-detail
  rows, tree/grouped data.
- **`packages/chat`** (`@symblight/chat`) — MD3 chat component: virtualized
  message list, docked composer (rich text, send, attachments, slash
  commands), streaming replies, typing indicators, pagination.
- **`packages/tree-view`** (`@symblight/tree-view`) — MD3 hierarchical tree
  view following the WAI-ARIA APG tree pattern: expand/collapse, single- or
  checkbox multi-select, roving-tabindex keyboard nav, typeahead, async
  branches.

Each package builds, tests, and documents itself independently but shares the
exact same toolchain and layout (see below). Package-specific architecture
notes live in each package's own `CLAUDE.md` (`packages/chat/CLAUDE.md` is the
most detailed) — read the relevant one before working inside a package.

## Commands

Run from repo root, across all packages:

```bash
pnpm install
pnpm build   # pnpm -r build
pnpm test    # pnpm -r test
pnpm lint    # pnpm -r lint
```

Scope any command to one package with `--filter`:

```bash
pnpm --filter @symblight/data-grid sb     # Storybook, port 6006
pnpm --filter @symblight/chat sb          # Storybook, port 6007
pnpm --filter @symblight/tree-view sb     # Storybook, port 6008

pnpm --filter @symblight/chat test
pnpm --filter @symblight/chat build
```

Or `cd` into a package and use its local scripts (`dev`, `build`, `sb`, `lint`,
`typecheck`, `format`, `test`) — identical script names across all three
packages. There's no root-level script to run a single test file; from inside
a package, pass the file pattern directly to `web-test-runner`, e.g.:

```bash
pnpm web-test-runner src/components/base/chat.spec.js --config web-test-runner.config.js
```

## Architecture

Every package follows the same stack and conventions:

- **Source**: JavaScript with JSDoc types, no `.ts` files — type-checked via
  `tsc --checkJs` (`typecheck` script, `tsconfig.typecheck.json`).
- **Build**: Vite, ESM output with `preserveModules: true` (one source file →
  one dist file), `.d.ts` generated by `vite-plugin-dts`.
- **Docs/dev**: Storybook (`@storybook/web-components-vite`), one port per
  package (6006/6007/6008).
- **Tests**: `@web/test-runner` + Playwright, spec files colocated as
  `src/**/*.spec.js`, run in Chromium.
- **Components**: Lit `@customElement`-decorated custom elements (2023-11
  decorator spec, transformed by Babel in build and test), MD3 theming via
  `--md-sys-color-*` tokens with component-level `--<pkg>-*` overrides.

Cross-package or design-process context lives under `.claude/plans/` at the
repo root (e.g. `tree-view.spec.md`, `commands.spec.md`, the `messages/`
subfolder of design docs for chat) — check there for the rationale behind a
non-obvious API before assuming it's undocumented.

## Notes

### The browser's main thread is expensive

Source: https://kciter.so/posts/the-expensive-main-thread/en/

The main thread is a shared, scarce resource — nearly all JS execution, DOM
manipulation, layout/paint calculation, and event handling run on it. Blocking
it freezes the entire UI. Frame budget on 60Hz is ~10ms; a task over ~50ms is
perceptible jank. It's not about how fast the code is, it's about how long it
holds the main thread.

Four strategies for work that must stay on the main thread:

- **Splitting** — break long work into chunks with yields in between (e.g.
  `await new Promise(r => setTimeout(r, 0))` between batches) so the browser
  can process queued rendering/input. Time-boxed splitting for animations uses
  `requestAnimationFrame` + `performance.now()` against a small per-chunk budget
  (e.g. ~5ms).
- **Batching** — collapse frequent events (scroll, resize, input) via
  debounce/throttle instead of reacting to every one.
- **Prioritizing** — control task queue order; React's scheduler uses
  `MessageChannel` instead of `setTimeout` for finer-grained control.
- **Deferring** — postpone non-urgent work.

When splitting isn't enough, move the work off the main thread entirely:

- **Compositor thread** — CSS animations/transforms run independently of the
  main thread, so they stay smooth even while JS is blocked.
- **Web Workers** — for work that can't be split into steps (e.g. parsing a
  multi-megabyte JSON response), offload the whole thing to a worker.
- **Eliminating the work itself** — the most elegant fix: don't optimize the
  work, remove it — virtualize lists (skip DOM for offscreen items), cache
  computed results, choose algorithms with fewer total operations.

Holding the main thread for a long time is equivalent to freezing the screen.
INP and TBT directly measure main-thread blocking duration.
