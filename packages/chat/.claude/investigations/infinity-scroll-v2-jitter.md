# `chx-infinity-scroll-v2` — расследование дёргания скролла (`@lit-labs/virtualizer@2.1.1`)

Дата: 2026-09-10. Story: `chat--pagination-v-2` (Storybook, порт 6007).

## Метод

Во внутренние файлы `@lit-labs/virtualizer` в `node_modules` добавлены временные
`console.log('[V2-DEBUG] ...')` (НЕ коммитятся, теряются при переустановке
зависимостей / `pnpm install`). Точки логирования:

- `Virtualizer.js`
  - `_init` — фактическое значение `_isScroller`
  - `_handleScrollEvent` — `correctingScrollError` + решение об `unpin()`
  - `_sizeHostElement` — какая ветка сработала (`sizer.transform` vs `host.minHeight`)
  - `_correctScrollError` — величина коррекции, вычисленная из `_scrollError`
  - `_adjustRange` — изменение диапазона отрисованных индексов (`_first`/`_last`/`_firstVisible`/`_lastVisible`)
  - `_positionChildren` — индекс/`top` самого верхнего отрисованного элемента
- `ScrollerController.js`
  - `correctScrollError` — START/END окна `correctingScrollError` (с `performance.now()`)
- `layouts/shared/BaseLayout.js`
  - `unpin()` — вызов + текущее значение `_pin`
  - `_setPositionFromPin` — pin, старая/новая `scrollPosition`, `scrollError`
- `layouts/flow.js`
  - `_calculateError` — срабатывание ветки `_first === 0`
  - блок применения `extentErr` — величина снэпа

Автоматизированная проверка через Playwright (`packages/chat/.debug-runner*.mjs`,
временные файлы, не коммитятся) — запуск Chromium, переход на
`http://localhost:6007/iframe.html?id=chat--pagination-v-2&viewMode=story`,
сбор `console` вывода, синтетические `page.mouse.wheel()`-скроллы разных
паттернов.

## Подтверждённые факты

### `_isScroller` действительно `true`

`config.scroller: true` в `infinity-scroll-v2.js` доходит до библиотеки как есть.
Значит размер контента (`scrollHeight`) выставляется через
`_getSizer().style.transform = translate(...)` на внутреннем `[virtualizer-sizer]`
дочернем элементе, а НЕ через `min-height` самого `.infinity-scroll-v2__scroller`.
Если раньше в DevTools казалось, что меняется именно `min-height` скроллера — это
либо единоразовый фолбэк `150px` из `_applyVirtualizerStyles()` (ставится один раз
при инициализации), либо CSS computed-style (`min-height: 0` из нашего же правила),
а не инлайн-стиль библиотеки.

### Причина №1 (подтверждена): начальный `pin` + гонка с `correctingScrollError`

При первом рендере `infinity-scroll-v2.js` ставит `layout.pin = {index: data.length-1, block:"end"}`,
чтобы сразу показать низ списка. Пока `pin` жив, `_setPositionFromPin()` на КАЖДОМ
`_reflow()` принудительно пересчитывает `_scrollPosition`, чтобы запиненный индекс
оставался у нижнего края — с реальными логами это видно как серия
`_setPositionFromPin` → `correctScrollError: START` сразу после навигации, пока
идёт первоначальное измерение реальных высот сообщений (значения `v` в
`_sizeHostElement` растут: `1 → 2800 → 4224.44...`, сходясь к финальному).

`pin` снимается (`unpin()`) только когда `_handleScrollEvent()` увидит scroll-событие
с `correctingScrollError === false` — то есть НЕ являющееся собственной коррекцией
библиотеки (`correctingScrollError` держится `true` ~2 rAF после каждого вызова
`correctScrollError()`). Если первый пользовательский scroll-тик попадёт в это
защищённое окно — `unpin()` будет no-op (`_pin` всё ещё не `null`), и на следующем
reflow `_setPositionFromPin()` опять силой потянет вид к запиненному индексу —
видимый "прыжок назад".

**В автоматических прогонах через Playwright эта гонка НЕ воспроизвелась** — во
всех трёх протестированных паттернах скролла (см. ниже) `unpin()` срабатывал по-настоящему
уже на первом же синтетическом тике. Вероятная причина: CDP-инжектированные
`wheel`-события не воспроизводят точный тайминг/pacing настоящего трекпад-скролла
(компоновка на уровне композитора vs `setTimeout`-пейсинг в скрипте) — то есть
гонка реальна по коду, но её физический репрод требует настоящего железа/ввода.

### Причина №2 (НОВАЯ, подтверждена логами): `restoreAnchor()` сам создаёт скрытый `pin`

При подгрузке истории `ScrollBehaviourControllerV2.js`'s `restoreAnchor()` вызывает
`element(newIndex).scrollIntoView({block: "start"})`, чтобы вернуть якорный элемент
на прежнее место после `prepend`. По исходникам библиотеки: если запрошенный
индекс **вне текущего отрисованного диапазона** (типичная ситуация сразу после
prepend — новые индексы ещё не отрисованы), `scrollIntoView()` не скроллит
напрямую, а **неявно выставляет `layout.pin`** (`_scrollElementIntoView`) — то
есть создаёт РОВНО ТОТ ЖЕ механизм, что и начальный `pin` из Причины №1, с той
же самой гонкой снятия.

Подтверждено логом реального прогона:
```
_setPositionFromPin: pin = {index: 40, block: start} ... newScrollPosition = 4838.64 scrollError = -4838.64
correctScrollError: START ... {top: 4838.64}
```
— несколько таких коррекций подряд (~600мс), пока идёт домер реальных высот
только что подгруженных элементов (`v` скачет: `9785 → 14677 → 14007 → 14230 → 14141...`),
и лишь потом реальный `unpin()` (не no-op). Это ровно объясняет более раннее
наблюдение "`correctScrollError: START {top: 4790.96}` при подгрузке истории" —
и, вероятно, весь класс дрейфа/мигания на видео при первом load-more.

**Значит корень этой проблемы — не столько в самой библиотеке, сколько в нашем
собственном `restoreAnchor()`**: он попадает в "out-of-range scrollIntoView" ветку
почти всегда сразу после prepend, каждый раз порождая новый скрытый pin.

### Причина №3 (теоретическая, отдельный кейс): снэп к началу/концу списка в `FlowLayout._calculateError()`

Независимо от `pin`, у `FlowLayout` есть свой anchor-based механизм коррекции
(`flow.js`, `_calculateError()`):
```js
_calculateError() {
  if (this._first === 0) return this._physicalMin;
  else if (this._physicalMin <= 0) return this._physicalMin - this._first * this._delta;
  else if (this._last === this.items.length - 1) return this._physicalMax - this._scrollSize;
  ...
}
```
Когда отрисованный диапазон достигает индекса `0` (или последнего индекса) ТЕКУЩЕГО
массива `items`, layout принудительно "прижимает" контент так, чтобы элемент с
индексом 0 (или последним) точно совпадал с началом/концом общей высоты — компенсируя
накопленную ошибку оценки размеров. Это НЕ связано с `pin`.

Это реальный, отдельный источник "прыжка к первому элементу" — но в story
`PaginationV2` всего `PAGINATION_TOTAL_HISTORY` (≈1000) сообщений истории, так
что `_first === 0` физически недостижим за один скролл сразу после инициализации —
туда можно попасть только исчерпав всю историю (после множества load-more).
**Автоматической проверкой это не подтверждено** (в `.debug-runner3.mjs` дошли до
`scrollTop: 4560` из `scrollHeight: 9785` — что уже после одного `load-more`, но
далеко не до глобального начала массива) — лог `_calculateError: _first===0` ни
разу не сработал. Скорее всего это НЕ причина зарепорченного бага "прыжок дважды
сразу после инициализации", а отдельный, потенциально существующий баг на
самом конце истории (стоит перепроверить отдельно, когда `hasMore` станет `false`).

## Баг "прыжок назад к первому элементу, ровно 2 раза, потом никогда" — не воспроизведён автоматически

Три протестированных паттерна синтетического скролла через Playwright:
1. `mouse.wheel(0,-120)` × 25, пауза 40мс между тиками.
2. "Momentum"-подобный: 90 тиков с экспоненциальным затуханием (`v *= 0.965`), пауза 8мс.
3. Грубый скролл почти к началу + тонкий "momentum" burst прямо на границе.

Во всех трёх — `unpin()` срабатывает по-настоящему уже на первом тике (`_pin`
сразу становится `null`), повторных силовых pin-коррекций после начального
settle не возникает. Т.е. гонка из Причины №1 в коде существует и объясняет
класс бага, но конкретно эту гонку не удалось спровоцировать через
CDP-инжектированные wheel-события — вероятно, из-за иного тайминга по сравнению
с реальным трекпадом/мышью.

**Рекомендация**: для точного захвата этого конкретного случая логи нужно смотреть
живьём в реальном браузере с реальным вводом (как ты и делал раньше) — текущая
инструментация (`unpin`, `_setPositionFromPin`, `correctScrollError` START/END)
уже на месте и должна поймать гонку, если она там есть.

## Фикс Причины №2 — применён и проверен

`restoreAnchor()` в `ScrollBehaviourControllerV2.js` переписан: убран
`element(newIndex).scrollIntoView({block:"start"})`-путь (который создавал
скрытый `pin` для вне-диапазонного индекса), теперь всегда используется ручной
diff-цикл по `getBoundingClientRect()` (он уже существовал как fallback, просто
не был основным путём) — он не трогает `layout.pin`/`correctingScrollError`
вообще, поэтому не может участвовать в этой гонке. Заодно убран ставший мёртвым
`#findIndexByKey()` и опция `itemKey` у `ScrollController` (была нужна только
для него).

Проверено тем же Playwright-сценарием (`.debug-runner.mjs`) до/после:

| | до фикса | после фикса |
|---|---|---|
| Новый `pin` от `restoreAnchor` при load-more | `{index: 40, block: "start"}` — создаётся | не создаётся вообще |
| `unpin()` с реальным (не `null`) `_pin` за сценарий | 2 раза (init + restoreAnchor) | 1 раз (только init) |
| Крупнейшая `correctScrollError` при load-more | `~4838px` (одноразовый снэп) | `~958–1129px` (обычная мелкая коррекция) |

Остаточный дрейф общей высоты (`_sizeHostElement`'s `v`) при досчёте реальных
размеров подгруженных сообщений (`8660→9877→9785`, `14677→13157→12844→12551`)
никуда не делся — это Причина, не связанная с `pin` (оценка/усреднение размера
непромеренных элементов), сегодня не трогали.

`tsc --noEmit` чист (кроме двух pre-existing, не связанных с этим фиксом
ошибок: `#resizeObserver` в этом же файле и `index` в `infinity-scroll-v3.js`).

## После фикса Причины №2: прыжки при медленном скролле всё ещё есть

Ручная проверка (не автоматизация) после фикса `restoreAnchor()`: **при медленном
скролле прыжки не пропали.** Это ожидаемо — фикс убрал только скрытый `pin` при
`restoreAnchor()`/load-more (Причина №2), а не общий механизм, который может
проявляться при любом скролле независимо от load-more.

Уточнение от пользователя про конкретно баг "прыжок дважды": он происходит так —
скроллишь, первое сообщение (то, что было видно изначально) пропадает из
видимости → откат. Скроллишь дальше, ещё одно сообщение пропадает → снова откат.
После этого откатов больше нет, скролл идёт гладко.

Проверены две гипотезы под этот паттерн:

1. **`anchorErr` в `flow.js`** (строки 296-308) — отдельный от `pin` anchor-based
   механизм: если "заякоренный" элемент выходит за физические границы (типично —
   когда его размер ещё не измерен реально и оценка разошлась), layout силой
   сдвигает `_scrollPosition`. Гипотеза была: первые 1-2 смены якоря на ещё
   неизмеренных элементах дают ровно "два отката, потом стабильно". Залогировано
   (`anchorErr snap applied`) — **при живом ручном репродюсе НЕ сработало ни разу**
   в момент прыжка. Гипотеза не подтвердилась (по крайней мере не для этого
   конкретного случая).
2. Вместо этого в момент прыжка сработал `_adjustRange CHANGED`
   (`first: 24→23, last: 39→39, firstVisible: 34→34, lastVisible: 38→38`) — но
   **`firstVisible`/`lastVisible` не изменились**, то есть реально видимое окно
   не сдвинулось: это просто безобидный домонт ещё одного элемента в невидимый
   буфер сверху. Скорее всего просто совпал по времени с прыжком, а не является
   его причиной.

**Итог: причина именно этого "прыжок дважды" бага всё ещё не найдена.** Ни одна
из проверенных гипотез (`pin`-гонка, `anchorErr`, `_calculateError`/`extentErr`,
`_adjustRange`) не выстрелила именно в нужный момент при живом репродюсе. Вся
инструментация (`[V2-DEBUG]` логи, см. список выше) остаётся на месте.

   не в самой библиотеке).
