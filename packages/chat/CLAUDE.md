# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

From this package directory (`packages/chat`):

```bash
pnpm sb              # Storybook dev server (port 6007)
pnpm dev             # Vite dev server
pnpm build           # Build to dist/ (clears dist/ first)
pnpm test            # Run tests with @web/test-runner + Playwright
pnpm lint            # ESLint
pnpm typecheck       # tsc --noEmit (JSDoc type-check, no emit)
pnpm format          # Prettier
```

From the monorepo root:

```bash
pnpm --filter @symblight/chat sb
pnpm --filter @symblight/chat test
pnpm --filter @symblight/chat build
```

Tests match `src/**/*.spec.js` and run in Chromium via Playwright. There is no flag to run a single test file via the npm script — pass the file pattern directly:

```bash
pnpm web-test-runner src/components/base/chat.spec.js --config web-test-runner.config.js
```

## Architecture

This is a pnpm workspace package (`packages/chat`). Source is **JavaScript with JSDoc types** — no `.ts` files. Type-checking runs via `tsc --checkJs`.

### Component tree

```
chx-chat                    (src/components/base/chat.js)
├── chx-message-list        (src/components/message-list/message-list.js)      — consumer-authored, optional
│   ├── chx-infinity-scroll (src/components/infinity-scroll/infinity-scroll.js) — generic virtualized list, see below
│   │   └── chx-message      (src/components/message/message.js)               — always the library's; restyle via ::part()
│   ├── chx-typing-indicator    (src/components/typing-indicator/…)            — standalone, consumer slots it in, see below
│   └── chx-streaming-indicator (src/components/streaming-indicator/…)         — standalone, consumer slots it in, see below
└── chx-message-composer    (src/components/message-composer/message-composer.js) — consumer-authored, required
    └── chx-textbox         (src/components/textbox/textbox.js)
```

`chx-chat` is the single public export (`src/index.js`); `chx-message-list`/`chx-message-composer` still register globally the moment `chx-chat`'s module loads (`chat.js` keeps side-effect-importing both purely for `customElements.define()`), but **`chx-chat` no longer renders either itself** — they're plain light-DOM children the consumer places directly inside `<chx-chat>`, same as `chx-command-field` already was:

```html
<chx-chat>
  <chx-message-list slot="message-list"></chx-message-list>
  <!-- optional -->
  <chx-message-composer slot="message-composer" placeholder="Write your prompt...">
    <!-- required in practice -->
    <md-button slot="actions">…</md-button>
    <!-- composer's own slots, not chx-chat's -->
  </chx-message-composer>
</chx-chat>
```

`chx-chat`'s template is two named slots, `message-list` and `message-composer` (layout via `chat.css`'s `::slotted(chx-message-list)`/`::slotted(chx-message-composer)` rules — `order` + `flex: 1 1 auto` on the list, `align-self: center` on the composer, so DOM order in the consumer's markup doesn't matter). Each requires its own `slot="message-list"`/`slot="message-composer"` attribute — there's no default slot to fall back on, an unslotted list/composer simply doesn't render (same "no slot, no render" contract `command-field` has one level down, see below). Because the composer is no longer chx-chat's own template child, chx-chat can't bind Lit properties onto it directly — `loading` is pushed onto whatever composer is currently slotted via the private `#pushComposerProperties()`, called both reactively (`updated()`) and on the `message-composer` slot's own `slotchange` (`#handleMessageComposerSlotchange`, covers a composer that gets (re)assigned after that prop was already set); `chx-message-list` gets the same treatment via `#pushMessageListProperties()`/`#handleMessageListSlotchange` on the `message-list` slot. The same push also hands both children chx-chat's API registry (see "Public API" below). `chx-send-message`/`change` are listened for via plain `addEventListener` on the `chx-chat` host itself (both events bubble/compose, same as any DOM event) rather than a template event binding. The four old `leading`/`actions`/`flight-icon`/`attachments` passthrough slots on `chx-chat` are gone — that mechanism only worked because chx-chat used to own the composer's light DOM declaratively; consumers now target `chx-message-composer`'s own slots directly, as shown above. `chx-chat` no longer has a `label` property either — it was really just a placeholder string in practice (every story/doc passed a hint like `"Write your prompt..."`), so it's gone in favor of setting `chx-message-composer`'s own pre-existing `placeholder` property directly, which now also doubles as the editor's `aria-label` (see "Composer input model" below).

`chx-command-field` (`src/components/command-field/command-field.js`) is a sibling component — consumers slot it in via `<slot name="command-field">` on `chx-message-composer` itself, not `chx-chat` (moved there from `chx-chat` — command-fields are input-path plumbing, not chat-level orchestration, so `chx-message-composer` discovers and tracks them directly, same "no slot, no render" contract as `message-list`/`message-composer` above). It's currently a pure trigger (declares `commandCharacter`, renders nothing) — not yet wired into the composer's input path, see "Composer input model" below.

### Public API — namespaces + `ChatController`

Consumer-facing imperative API is **domain namespaces** on `chx-chat`, never flat element methods: `delivery`, `store`, `presence`, `viewport`, `input`, `attachments` (getters returning stable frozen facades). Consumer docs: `src/docs/public-api.md`; design and rationale: `.claude/plans/chat-public-api.spec.md` (repo root). Old element methods (`retry`, `setTyping`, `addMessage`, `cache`, `messageListElement`, composer `setText`/`insertAtRange`, list `scrollToBottom`/`list`, …) were removed outright — don't reintroduce flat methods; add to a namespace's typedef instead.

- **Registry** — `src/api/ApiRegistry.js`, generic (no chat vocabulary, meant to be reused by data-grid/tree-view later). One owner (a Lit host) per namespace via `register(ns, host, impl, snapshot?)` → unregister; facades resolve the current owner per call and fall back to `CHAT_API_DEFAULTS` (`src/api/chat-api-defaults.js`, deep-frozen, typed `ChxChatApi` — it's the tsc-checked list of method names) with a one-time console warning. A second owner logs `console.error` and replaces the first.
- **Contract** — `src/types/api.js` (`ChxChatApi` + one typedef per namespace, re-exported as types from `index.js`). Reads are `get*`/`is*`/`has*`; a trailing optional `conversationId` defaults to the active conversation (`DeliveryController.statusFor`/`busyFor`/`stop(id)`, `PaginationController.hasMoreFor`/`isLoadingFor` exist for this).
- **Owners** — `chx-chat` registers `delivery`/`store`/`presence` in its constructor. `chx-message-list` registers `viewport`; `chx-message-composer` registers `input` and, on behalf of its slotted `chx-attachments` (after `customElements.whenDefined`), `attachments`. Both children receive the registry from `chx-chat`'s `#push*Properties` via the symbol-keyed `[CONNECT_REGISTRY](registry)` method (`src/api/keys.js`, not exported from `index.js`), idempotent, and unregister on disconnect.
- **Change notification** — owners never call `notify()`. `register()` adds a tiny controller to the owner host; its `hostUpdated` diffs the namespace's `snapshot()` (shallow `Object.is`) and fires `change`. Exception: `chx-attachments`' cards are light-DOM children and don't re-render it, so the composer calls `registry.check("attachments")` on `chx-attachments-change`.
- **`ChatController`** (`src/controllers/chat/ChatController.js`) — for a consumer's own Lit element: the six namespaces plus reactive `status`/`busy`/`messages`/`hasMore`/`loading`/`typing`/`awayFromBottom`/`files`, `connected`, `isAvailable(ns)`. Re-renders only for namespaces it actually read (two sets swapped in `hostUpdated` — not cleared in `hostUpdate`, because Lit runs `willUpdate()` before controllers' `hostUpdate()`). Reactive getters read via `registry.current(ns)` (no warning). Context: `chatApiContext` (`src/context/chat-api-context.js`), with a `customElements.whenDefined("chx-chat")` re-request for hosts defined before `chx-chat` — `@lit/context` exports the event class as `ContextEvent`.

**Internal cross-element wiring never uses context or `closest()`.** `chat.js` imports `message-composer.js`/`message-list.js` before `ChxChat` is defined, so with markup already in the DOM the children upgrade first and a light-DOM `ContextConsumer` request is lost for good (`@lit/context` only fixes that with a global `ContextRoot`). Instead: **events up** (`chx-command-picker`/`chx-attachments` dispatch `chx-insert-chip` `{node, target?}`, bubbling, not composed — the composer listens on itself; `target` given → `insertAtRange`, omitted → caret), **push down** (`#push*Properties`, `CONNECT_REGISTRY`), and **slotchange-tracked getters** (`getTriggerFields`) and live child lookups (`getExtensions`). `chx-chat`'s drop target reads its own light DOM (`#attachmentsElement`); `ScrollMemoryController` goes through `viewport`. Standalone `chx-infinity-scroll` and `chx-attachments` keep their public methods; `focus()` overrides on composer/textbox stay (native method, composer has no `delegatesFocus`).

### Controller location

Every `*Controller.js` file in the package — whether a real host-bound `ReactiveController` or a plain stateful/callback-driven helper — lives under `src/controllers/`, regardless of which component(s) it's used by; nothing colocates a controller inside its consuming component's own folder. `src/controllers/` is subdivided by feature, one folder per consuming component/area, not flat:

- `src/controllers/chat/` — `chx-chat` orchestration: `ChatController` (the one **public** controller, exported from `index.js` — see "Public API"), `DeliveryController` (owns sending itself — `deliver`/`retry`/`regenerate`/`#deliverRegenerate` moved here out of `chat.js`), `RealtimeSyncController`, `ConversationModeController`, `ScrollMemoryController`, `PresenceController`, `PaginationController` (+ its spec), `StreamController`, `DropTargetController`.
- `src/controllers/infinity-scroll/` — `chx-infinity-scroll` mechanics: `InfinityScrollController`, `VirtualListController`, `PlainListController`, `LoadMoreController`, `VisibilityController`, `PinController`, `BottomSentinelController`.
- `src/controllers/message-list/` — `chx-message-list` row/scroll/focus behavior: `StatusController`, `StickyController`, `ReadTrackingController`, `DividerController`, `FocusBehaviorController`.
- `src/controllers/code-block/` — `chx-code-block` editing: `EditableBodyController`.

Non-controller collaborators (`PartRenderer`, `RowMeasurer`, `StickToBottom`, `caret.js`, `undo-stack.js`, and `message-list/`'s pure helpers — `group.js`'s `groupAt()`, `parts.js`, `estimate.js`'s `estimateMessageSize()`, `authors.js`'s `authorFor()`, `interior-tabbing.js`) stay colocated with their component, not under `src/controllers/`. A stateless helper is a function, not a class: same-author grouping is `groupAt(messages, index, hasDividerBefore)`, and the agent parts' row-compact mirroring is `consumeRowCompact(host)` in `src/context/message-row-context.js`.

Conventions every controller follows: one `#config` object typed by a `@typedef` (never a `#getX` field per callback); one-line comments, keeping only non-obvious constraints and ordering rules (history and rejected alternatives belong in this file or a spec); and shared helpers instead of local copies — `indexById(messages)` (`src/utils/messages.js`, WeakMap-memoized id → index), `pollFrames(find)` and `distanceToBottom(el)` (`src/utils/dom.js`). Repeated multi-step flows get one private runner: `DeliveryController.#run()` covers send and regenerate, `PaginationController.#fetchPage()` covers the first and older pages. When adding a new controller, put it in the matching feature folder under `src/controllers/` from the start (creating a new feature folder if none fits) rather than beside the component that first needs it.

### Composer input model

`chx-message-composer` composes `chx-textbox` — a from-scratch MD3 filled-field container (replacing an earlier `md-text-field`-based implementation, which only exposed `leading`/`trailing` slots and had no room for an attachments row above the input). Unlike the original design, **`chx-textbox` now owns the ProseMirror `EditorView` directly** — it renders `.message-composer__input-content` (a **static, binding-free** `<div>`, see below) itself and constructs the `Editor` facade (`src/editor/Editor.js`) against it in `firstUpdated()`; `chx-message-composer` never touches ProseMirror or the mount div at all. `chx-textbox` is form-associated (`FormControlMixin` + `requiredValidator` from `@open-wc/form-control`, `shadowRootOptions.delegatesFocus = true`) and configured by the composer via plain properties — `placeholder` (also applied as the editor's `aria-label` — see `#mountEditor`/`updated`), `getTriggerFields` (a function returning the live `Map` `chx-message-composer` itself now tracks, via its own `command-field` slot's `#handleCommandFieldSlotchange` — moved down from `chx-chat`, see above), `getExtensions` (editor extensions, see below) — and reacts to a bubbling `chx-textbox-change` event (detail `{value, html}`, replaces the composer's own value on every doc-changing transaction) and `chx-command-selected` (dispatched by `chx-textbox` directly now, no composer pass-through needed). Public methods `getValue()`/`getHTML()`/`focus()`/`focusEnd()`/`clear()`/`setText()`/`insertAtRange()`/`insertChip()` are how the composer drives it through its private `#textbox` getter — e.g. on send: `getValue()`/`getHTML()`/`focus()`, then `clear()`. They stay public only because the composer calls them across its own shadow boundary; consumers go through `chat.input` instead. It exposes three slots — `leading` (e.g. a future "+" attach/upload trigger), `attachments` (attachment previews, rendered above the input), and `trailing` (the send button/actions-wrapper, composer-authored) — no default slot anymore, since the mount div is chx-textbox's own internal node, not something the composer slots in. `leading`/`attachments`/`trailing` reflow between a one-line and a stacked 3-row layout **purely via CSS** (`textbox.css`'s `:has(.textbox__attachments ::slotted(*))` rule forces the content column onto its own line once `attachments` holds anything, no JS layout state).

Schema (`src/editor/schema.js`), keymap (`src/editor/keymap.js`), forced-plain-text paste (`src/editor/paste-plugin.js`), and the placeholder decoration plugin (`src/editor/placeholder-plugin.js`) all live under `src/editor/`, consumed only by `Editor.js`/`textbox.js` now. The mount node must never sit inside a Lit conditional (`when()`/etc.) or carry a dynamic binding (e.g. a reactive `class`), confirmed live to silently kill the view with no console error otherwise. On send, the composer dispatches a `chx-send-message` CustomEvent with `{ value: string, html: string }` in `detail`. The pre-ProseMirror `ContentTextoFormatter` (`src/text-formatter/text-formatter.js`) is still present but not wired into this path — commands are a not-yet-started migration onto the same engine (see `.claude/plans/commands.spec.md`).

Pastes collapse into a `paste` schema node only through **editor extensions** — `chx-message-composer`/`chx-textbox` never name them. Two ship, as independent features (`@symblight/chat/composer`): `<chx-paste-long-text>` (`src/components/paste-long-text/`, `paste-threshold`+ lines → "N lines" `<chx-paste-chip>`, see `src/docs/paste-chip.md`) and `<chx-code-block-paste>` (`src/components/code-block-paste/`, Lezer-heuristic code detection in `detect-language.js` → editable `<chx-code-block>`, see `src/docs/code-block-paste.md`). They were one element until 2026-10-08; split because they're different features.

The contract is `src/editor/extension.js` — an element exposing an `[EDITOR_EXTENSION]` getter (`Symbol.for`) returning `{priority?, handlePaste?, buildPasteElement?, updatePasteElement?}`. The composer's stable `#getExtensions()` collects them from its **direct children, live at paste/render time** (no slot, no observer — so no upgrade-order problem) and passes it to `chx-textbox` → `Editor`. Nothing needs ProseMirror `reconfigure()`: the `paste` node/plugin/node-view are always present and inert with no extensions (every paste inline).

- **Paste** — `paste-plugin.js` asks `handlePaste(text, lines)` in `byPastePriority` order (highest `priority` first, ties keep child order); the first non-null return becomes the node's `data`. `chx-code-block-paste` has `priority: 1`, so code wins over the long-text threshold (explicitly chosen); its `maxLines` (2000) caps detection, which parses the whole paste once per candidate language on the main thread.
- **Ownership** — one `paste` node type for both; `data.kind` (`"long-text"` / `"code"`) names the owner. `PasteNodeView` takes the first extension whose `buildPasteElement` returns non-null (each returns `null` for a foreign `kind`), remembers it, and calls its `updatePasteElement` on node updates (undo/redo). Unclaimed nodes fall back to `defaultBuildElement` (a `<chx-paste-chip>`).
- **Sync-back is generic** — `PasteNodeView` knows no code-block events. A built element dispatches `PASTE_CHANGE_EVENT` (`chx-paste-change`, `{text?, data?}`, `text: ""` deletes the node) and `PASTE_BOUNDARY_EVENT` (`chx-paste-boundary`, `{direction}`) on itself. `chx-code-block-paste.#bind` translates `chx-code-block-change`/`-lang-change`/`-boundary` into those, outside `buildElement()`, so an override keeps syncing. Arrowing *into* an editable element is `keymap.js`'s DOM-shape-based `arrowHandler`.
- **Overrides** — `buildElement()` on both, plus `classify()`/`updateElement()` on `chx-code-block-paste` — plain overridable methods, same shape as `chx-command-picker.buildChip`. Named `buildElement`, not `buildChip`: it can return any element.
- **Post-send** — `attrs.text` round-trips losslessly through `getValue()` (an explicit `paste` branch in `serialize.js`'s `toPlainText`) and `getHTML()` (`<span data-paste-lines data-kind …>` from the node's `toDOM`, `data` keys as `data-*`). Each element exports an `InlinePartRule` keyed on `data-kind` — `longTextPastePartRule` (`type: "longText"`) and `codeBlockPastePartRule` (`type: "code"`) — for `splitMessageParts`/`createSplitOnSendHandler` + `partElements`.

`insertPasteChip` in `paste-plugin.js` lands the caret one space after the chip, same "reuse a following whitespace instead of adding a second one" logic as `Editor.js`'s `resolveCommand`.

### Message list internals — virtualization moved out to `chx-infinity-scroll`

`chx-message-list` no longer owns virtualization, scroll-position management, or load-more detection itself — that's `chx-infinity-scroll`, a generic, message-agnostic component (`.data`/`.itemKey`/`.renderItem`/`.estimateItemSize`/`.overscan`/`.paddingStart`/`.paddingEnd`/`.scrollMargin`/`.useScrollendEvent`/`.scrollBehavior`/`.contentAlign`/`.buffer`/`.hasMore`/`.loading` in; `.onLoadMore` callback awaited directly for older pages, `.onAwayFromBottomChange` + `.onScrollerKeydown`/`.onScrollerFocusin` callbacks out; `scrollToIndex()`/`scrollToBottom()`/`remeasure()`/`dropMeasurements()` methods; `footer` slot; `chx-scroll-to-bottom` and `chx-load-more-start`/`-error`/`-end` events). It's built on `@tanstack/lit-virtual`'s own native `anchorTo: "end"` + `followOnAppend` config, not a hand-rolled scroll controller. It needs virtual-core 3.17.11 or later (`@tanstack/lit-virtual` 3.14.2): when a width change re-wraps every row at once, virtual-core compensates each row above the view right away, before the canvas has grown, and the browser clamps those writes; 3.17.11 replays the clamped part once the canvas grows (`_retryClampedAdjustment`). Before it, a column opening beside the chat lost the pin and the bottom. Vite bundles both packages into `dist/node_modules`, so a consumer gets this library's versions, never its own. `.overscan`/`.paddingStart`/`.paddingEnd`/`.scrollMargin` (`number`, attributes `overscan`/`padding-start`/`padding-end`/`scroll-margin`, defaults `6`/`0`/`0`/`0`) and `.useScrollendEvent` (`boolean`, attribute `use-scrollend-event`, default `false`) are the public tuning surface onto the underlying `@tanstack/virtual-core` `VirtualizerOptions`, each mapping 1:1 to that library's own option of the same name. `count`/`getScrollElement`/`getItemKey`/`estimateSize`/`anchorTo`/`followOnAppend`/`scrollEndThreshold` stay exclusively owned by this component's own properties/opinionated bottom-anchoring defaults — no generic passthrough bag exists onto the rest of `VirtualizerOptions` (`gap`, `scrollToFn`, `isRtl`, `lanes`, etc.), only these five named knobs. `chx-message-list` forwards all five straight through, mirroring how `buffer`/`scrollBehavior`/`estimateItemSize` already are. `.overscan`/`.paddingStart`/`.paddingEnd`/`.scrollMargin` are genuinely live — `VirtualListController.sync()` diffs and re-`setOptions()`s them on every render, and virtual-core's own layout memo keys directly off `options.overscan`/`paddingStart`/`paddingEnd`/`scrollMargin`, so a later change takes effect on the next measurement pass. `.useScrollendEvent` is **not** — `@tanstack/virtual-core` only reads `options.useScrollendEvent` once, the one time it subscribes to the scroll element's offset (on first mount, in `observeOffset`); nothing tears that subscription down and re-reads the option when it changes later via `setOptions()`. So `sync()` deliberately excludes it from the live-diff set — it's applied once at `VirtualListController` construction time and is inert after the list has rendered content, unlike the other four. Two internal thresholds are deliberately *not* exposed here: tanstack's own `scrollEndThreshold` (`VirtualListController.js`, `8`, an internal resize-compensation band) and `LoadMoreController`'s unrelated `LOAD_THRESHOLD` (`450`, px from the top that triggers `onLoadMore`) — both stay hardcoded. `chx-message-list`'s own `#renderItem` builds a `<chx-message>` and hands it to infinity-scroll's `.renderItem` — infinity-scroll never knows what a "message" is. Its mechanics live in `InfinityScrollController` (composed of `VirtualListController` = the tanstack virtualizer, `RowMeasurer` = measuring a row only once its custom-element content actually exists, `StickToBottom` = re-pinning when a prepend lands into a not-yet-full viewport, `LoadMoreController` = awaiting `onLoadMore` near the top) plus `InitialBottomLock`, which keeps the first paint welded to the bottom through the measurement settle — all under `src/controllers/infinity-scroll/` (moved there from `src/components/infinity-scroll/` — see "Controller location" above), while `RowMeasurer`/`StickToBottom`/`InitialBottomLock` stay under `src/components/infinity-scroll/` as they're not controllers. `InfinityScrollController` is the only class that branches on `noVirtualization`; `chx-infinity-scroll`'s scroll methods just forward to it. `chx-message-list`'s `scroll-behavior="auto" | "smooth"` attribute (forwarded straight through to infinity-scroll) governs `scrollToBottom()`'s animation, for both an explicit `chat.viewport.toBottom()` and the automatic stick-to-bottom follow. (An earlier v1 built the same public surface on a hand-rolled `ScrollBehaviorController` firing a fire-and-forget `chx-load-more` event, and short-lived `chx-infinity-scroll-v2`/`-v3` experiments — all removed; this tanstack-native build, formerly `-v3`, is now the sole `chx-infinity-scroll`.)

`scroll-mode="pin-top" | "stick-bottom"` (default `"stick-bottom"`, on both `chx-message-list` and `chx-infinity-scroll`) is the agent-chat scroll model, kept separate from `content-align`, which stays purely layout (where an under-full list rests). `chx-message-list.#pinSentMessage` (in `willUpdate`) treats an own message appended at the tail as a send and calls `chx-infinity-scroll.pinToStart(id)` **before** the new `messages` reach infinity-scroll. That order is load-bearing: `PinController` (`src/controllers/infinity-scroll/PinController.js`) turns virtual-core's end-following off through `VirtualListController.setFollowing()`, which sets `scrollEndThreshold` to `-1` immediately, because `followOnAppend` checks the *previous* options. Once the row renders, `PinController` scrolls it to the top once, through `virtualizer.scrollToOffset()` so virtual-core's own offset never lags. A row taller than the view (a long prompt) is pinned by its end instead, halfway down the view (`InfinityScrollController.#pinOffset`): pinned by its top, the reply would start below the fold with following off. Virtualized, the first aim uses the row's estimate, so the pin stays pending and aims again once virtual-core has measured it (`isMeasured`). The reserved space below it is pure CSS. While a pin is active, `PinController` adds the `infinity-scroll__content_pinned` modifier class: `justify-content: flex-start` (regardless of `content-align`, so under `"end"` the space still falls below, never above) and `min-height: calc(100% + var(--_chx-pin-offset))`, where the variable is the pinned row's offset from the content top. The browser absorbs any growth or shrink below the pin in the same layout pass. A JS-sized spacer was tried first and failed: it always lags one layout behind, so a transient shrink got the scroll clamped. Two cases were confirmed live: a 1px scroll on the first send from rounding fractional padding, and the streaming indicator leaving the footer one update before the reply row landed, which clamped `scrollTop` and showed the previous turn. The offset only moves when rows above the pin change (a prepend), so it's refreshed in `hostUpdate` (virtualized, before render) and in `PlainListController`'s `beforeReconcile`. Following, gated by `PinController.following` in `StickToBottom`, `PlainListController`, and `InfinityScrollController`'s footer follow, stops on any upward scroll that leaves the very bottom (8px): rows above shrinking — a wider column re-wraps them — move `scrollTop` up while the view stays at the end. It resumes only when a user-driven scroll reaches the very bottom (8px) or on `scrollToBottom()`,. The pin clears when its message leaves `data`, e.g. on a conversation switch. In `"stick-bottom"` mode `following` is always `true`, so nothing changes there. Separately, in both modes, whether the view is "at the bottom" for following is a `BottomLatch` (`src/components/infinity-scroll/BottomLatch.js`): one instance owned by `InfinityScrollController`, updated once per scroll event in `handleScroll`, and injected into `StickToBottom` and `PlainListController`: a scroll that moves up *and* away from the end, past 8px, leaves it even inside `buffer`; only moving closer within `buffer` rejoins. Requiring the distance to change keeps compensation for a prepend or a shrinking row from counting as either. `InfinityScrollController.userGesture` is the one gesture handler: bound passive on the scroller for `wheel`/`touchstart`/`pointerdown`, and called from the scroller's `keydown`. Any of those ends the initial pin. A scroll gesture (`isScrollGesture()` in `src/utils/dom.js`: a vertical `wheel`, `touchstart`, `keydown`, or a `pointerdown` on the scroller itself, i.e. the scrollbar) is noted on `GestureGrace` (`src/components/infinity-scroll/GestureGrace.js`, the one owner of the 200ms window). Unless it's a key, which drives its own scrolls, it also pauses every follow for that window (`GestureGrace.pause()`), including virtual-core's own via `setFollowing(false)`, because a programmatic scroll before the gesture's first scroll event cancels the browser's wheel animation. It also clears virtual-core's private `scrollState`, which otherwise keeps re-aiming a smooth `scrollToEnd()` against the user for up to 5s. `chx-infinity-scroll.following` folds in the latch and the pause. The `footer` slot (typing/streaming indicators) sits outside both strategies' rows, so `InfinityScrollController` puts a `ResizeObserver` on it and follows its growth while `following` (`#followFooter`; the DOM's distance, not `isAtEnd()`, since virtual-core's end is the last row). It replaced `chx-message-list.updated()` re-sticking on a `typing`/`streaming` toggle through `scrollToBottom()`, which also fired `chx-scroll-to-bottom` and re-armed the pin for what was never an explicit request. Two more holds pause following the same way: a mouse/pen button held on the content (`#pointerHeld`; the click focusing a tall row makes Chrome scroll it into view, so `BottomLatch` ignores jumps while `held`), and, if that release leaves text selected in the list, `#selectionHeld` until `selectionchange` finds it cleared or `scrollToBottom()` runs. A plain click resumes on release. Chromium keeps a shadow tree's selection off `document.getSelection()` in some versions, so `#hasSelection()` asks the scroller's root first. A reply re-rendering under the selection can drop it, which correctly resumes following. In `PinController`, only a scroll within that window (`isUserScroll`, i.e. `GestureGrace.recent`) clears the resume suppression, so a click on a message's button or a wheel a nested code block consumed can't resume following. Without virtualization, `PlainListController.#followToBottom()` animates a follow only when it starts within one viewport of the bottom; catching up from farther away jumps. On first render the rows are 0px tall, so the first landing is near the top and the real one comes once they have height. Animating that catch-up showed the top first in Chrome. Smooth scrolling in this mode is a plain native `scrollTo({behavior: "smooth"})`; the browser animates it and cancels it on a user gesture. A JS `scrollTop` animation was used until 2026-10-20 and removed on request for simplicity: the arrow's long jump read as a jump in its first version, and the native scroll is what the user wants. Its trade-off is WebKit, below. Native smooth scrolls can fail in WebKit while a reply streams (confirmed live, 2026-10-19): a streaming part swapping its DOM makes the content shrink for one forced layout and regrow, which clamps `scrollTop`, often to 0. Chrome restores it through scroll anchoring; WebKit has none. Earlier, a smooth `scrollTo` issued in the frame the content grew was also silently dropped in Safari. The same clamp used to read as the user leaving the bottom, so `BottomLatch.update()` takes `{layoutJumps, contentChanged}`: without virtualization and with no recent gesture (`GestureGrace.recent`), an upward jump that comes with resized content, or rows mutated since the last scroll event (`PlainListController.takeContentChanged()`), is layout's. The same rule as use-stick-to-bottom ignoring scroll events during a content resize. Not when virtualized: rows measure on every upward scroll there, so a real one would be ignored. `"smooth"` scrolls drop to `"auto"` under `prefers-reduced-motion`.

`onAwayFromBottomChange` (which gates the `scroll-to-bottom` slot and feeds `StickyController`) is content-based, not scroll-height-based. `BottomSentinelController` puts one `IntersectionObserver` (root = scroller, `rootMargin` bottom = `buffer`) on `.infinity-scroll__end`, an empty element after the `footer` slot, so before any space reserved under `scroll-mode="pin-top"`. "Away" means that element is below the viewport plus `buffer`. Reserved blank space never counts, an empty list is never away, and there's no scroll handler or layout read. It's the same in both list modes. Following keeps its own scroll-height check (the shared `BottomLatch`), which are a separate concern.

`chx-message-list` itself is deliberately thin: it declares its properties, renders its template, and assembles one row. Everything else is a narrow collaborator, constructed in one block in the constructor — that block is the map of the component. `StatusController` is a real host-bound `ReactiveController`; `DividerController`, `ReadTrackingController` and `PartRenderer` take only named callbacks and no host, so they're testable without an element. `PartRenderer` stays colocated in `src/components/message-list/` (it's not a controller); the `*Controller.js` files live in `src/controllers/message-list/` — see "Controller location" above.

- **`StatusController`** — the `empty` / `initial-loading` / `ready` phase, the orthogonal `loadingHistory` overlay, and the `role="status"` text. Both used to be derived twice (once in the element's `#updateStatusText()`, again as the `when()` gates in its template), which is the same precedence ladder kept in sync by hand. It's a real controller for one reason: the streaming start/complete edge needs a diff against the previous pass, and `hostUpdate()` runs it right before `render()`, so nothing side-effecting is called from inside `render()` any more. The template now picks the phase with `choose()` instead of nested `when()`.
- **Bottom anchoring** — `#awayFromBottom` (fed by `chx-infinity-scroll.onAwayFromBottomChange`, also pushed to `StickyController` and the `viewport` snapshot), `chx-scroll-to-bottom-click` caught by a listener on the host (the affordance is slotted light DOM, so no template binding sees it), and `#scrollToBottom()`, reached publicly through `viewport.toBottom()` — the list has no public scroll methods. Was `BottomAnchorController` until 2026-10-19; inlined because it only held one boolean and forwarded two calls.
- **`PartRenderer`** — per-part rendering and its element cache, with the two different cache contracts documented in its own header (loose for a consumer's `partElements` renderer so it gets `previousElement`; strict for the built-in text/html path).
- **`ReadTrackingController`** also owns `shouldObserve`/`handleItemVisible`/`syncReadStates` outright now — those were previously host-side wrappers that only re-gated on `readTracking`, and `willUpdate` is down to one delegating line. The readState diff deliberately stays there rather than riding `handleItemVisible`'s existing array-reference check: an unread → read → unread round trip between two visibility events would compare its endpoints, see "unread" twice, and leave the message stuck in the fire-once set.
- **`#requestRerender()`** — one private method for the "`this.requestUpdate()` **and** `infinityScrollElement.requestUpdate()`" idiom, which was previously injected into `FocusBehaviorController` and hand-copied in two more places. Anything that changes how a row should look without changing `messages` has to go through it.

`FocusBehaviorController` (roving tabindex over messages) lives in `src/controllers/message-list/` — a real cross-component update-cascade bug was found and fixed live there: calling `this.#host.requestUpdate()` (host = `chx-message-list`) does **not** re-render `chx-infinity-scroll`, since none of the properties passed to it change by reference on a plain host re-render — Lit's `PropertyPart` skips re-setting them. `FocusBehaviorController` now takes an injected `requestRerender` callback that also calls `infinityScrollElement.requestUpdate()` directly. Likewise, focus-follow after `scrollToIndex()` can't rely on the host's own `hostUpdated()` firing again once the scrolled-to item mounts (infinity-scroll's own internal settling renders never cascade back up) — it polls via a capped `requestAnimationFrame` loop instead. The tab stop always sits on a rendered row: `keepOnRendered(rendered)`, called from `#renderItem`'s per-pass sweep, moves it to the rendered row nearest its old index when its row was virtualized away or its message is gone (a conversation switch), and clears a drill-in whose row went. With focus outside the list, it also moves to the newest fully visible row 150ms after scrolling settles (`#followViewport`, walking rows from the end), so Tab lands on what the user sees without scrolling; while focus is inside, keyboard navigation owns it. Before 2026-10-19 the stop was seeded once and stuck, so after older pages loaded no mounted row could be tabbed to.

### Conversation switches under `noVirtualization`

One list and one scroller serve every conversation, so a switch is an explicit step, not something rows imply: `ScrollMemoryController` asks `viewport.positionToSave()` when leaving (an offset, `undefined` for the bottom, `null` while the last switch is still settling, so a mid-switch offset is never saved) and calls `viewport.showPosition()` in `chx-chat`'s `updated()`, right after the list got its new `messages`. `InfinityScrollController.showPosition()` resets the latch, the pin and the anchor, then `PlainListController.show()` re-applies the offset or the bottom on every reconcile until layout has been quiet for `SETTLE_QUIET` or a scroll gesture takes over. Scroll events meanwhile are layout's, never judged. Virtualized mode keeps its own handling: it always saves the offset and only restores it.

### `#renderMessage` — a template, not an element

A row is a Lit template, not an element assembled by hand. `#renderMessage` returns a `TemplateResult`; `own`/`busy`/`unread`/`part`/`exportparts`/`tabindex`/`aria-label`/`actionable` are ordinary bindings, and **no message-element cache exists** — `chx-infinity-scroll`'s own `repeat()` is keyed by `message.id`, so Lit reuses each row's DOM itself. This only became possible once `messageElement` was gone: while a consumer could replace the row wholesale, neither the bindings nor the part names could be guaranteed on every row.

A row is `<chx-message-row>` (internal, light DOM: roving focus, ARIA, `data-message-id`, the `messageRowContext` provider) around a `<chx-message>`. Appearance is CSS (the part vocabulary above); content is `partElements`. A consumer can also give every row its own markup — avatar, actions, meta — with a **pattern**: `<chx-message slot="message">` inside `chx-message-list` (see `message.stories.js`'s `MessagePattern`). The `message` slot is `hidden` and never projected — one `<slot>` projects one set of nodes, and rows are virtualized — it only lets `#handleMessagePatternSlotchange` find the pattern. `#renderMessage` deep-clones it per message (`#messageClones`, by id, swept with the other per-pass caches) and renders the parts after the clone's own children with `render(parts, clone)`, which only ever manages that range. A `MutationObserver` on the pattern drops every clone on a consumer change, ignoring the attributes `chx-message` reflects on itself (`MESSAGE_OWN_ATTRIBUTES`). Ids inside the pattern are warned about, since every row duplicates them. Plain markup is copied as is; a custom element in it reads the row's state from `messageRowContext`.

Three things about it are load-bearing and easy to undo by accident:

- **A row re-renders only when its `guard()` deps change** (`#renderItem`). `guard` is per child part, so a row (re)entering the DOM always renders. Anything a row reads that isn't derived from its message object must be in the deps, or go through `#invalidateRows()`. A skipped row still counts as rendered for the microtask sweeps (`#pendingRenderedMessageIds`, `PartRenderer.keep()`).
- **`ensureSeeded()` runs before the guard, not inside it.** The `isFocused` dep and the `tabindex` binding would otherwise read an unseeded focus state on the very first row.
- **Interior tabbing needs an element directive, not `ref()`.** Suppressing the Tab order of the light-DOM children a consumer's `partElements` renderer produced is the one thing no binding can express — Lit doesn't own those nodes. `interiorTabbing()` (`interior-tabbing.js`, an element directive whose `update()` runs whenever the row renders, and whose `MutationObserver` on the row and the open shadow roots inside it re-runs the sync when a part adds content later, since a guarded row gets no later render pass) calls `FocusBehaviorController.syncInteriorTabbing`; `ref()` would fire only when the element itself changes, never when its children do. Both halves of that walk are idempotent, which is why `#drillInto`/`#exitDrillIn` can still call them directly instead of waiting for a re-render.
- **`DividerController.wrap()` always returns a `[divider, row]` pair**, with `nothing` in the first slot when no divider is due. Alternating between a bare value and an array makes Lit tear the ChildPart down and rebuild it, which would throw away the row's `<chx-message>` every time a date boundary appears or disappears.

Two non-problems, both checked rather than assumed: `.map()` over the parts needs no `repeat()`, because `PartRenderer` returns real Nodes — Lit's positional iterable commit already yields the right order and skips re-inserting an identical node. And `RowMeasurer` is unaffected: its `#pendingChild()` catches "upgraded but never rendered" via `hasUpdated === false`, and an element built by `document.createElement` hit that same branch, so the measurement timing did not move.

### Typing / streaming / initial-loading indicators — opt-in slots

`chx-message-list` exposes two slots, `typing` and `streaming`, each gated by a boolean property (`typing`/`streaming`) pushed down from `chx-chat`. **Neither has default/fallback content, and `chx-message-list` does not import or auto-register the components that fill them** — same connection as `<chx-command-field>`/`<chx-command-picker>` already establish: a standalone component the app imports and slots in itself (`<chx-typing-indicator slot="typing">` inside `<chx-message-list>`), or nothing renders, full stop, regardless of what the boolean says. An earlier pass of this bundled a default `<chx-typing-indicator>` as the slot's native fallback content — reverted, directly requested, to match the command-field precedent exactly rather than half-matching it. These gated slots (`typing`, `streaming`, `loading-history` and `scroll-to-bottom`) are always rendered and toggled with `?hidden`, never inserted or removed with `when()`. Inserting or removing a `<slot>` in the list's shadow root aborts a running smooth scroll in WebKit (confirmed live). Removing `scroll-to-bottom` on reaching `buffer` used to stop the affordance's scroll ~90px short; virtualized mode then finished it after virtual-core's 150ms `isScrolling` debounce, which looked like a pause.

- **`typing`** — `chx-chat.presence.setTyping(isTyping, conversationId)` or `adapter.subscribe`'s optional `onTyping` handler, both funnel into `PresenceController` (`src/controllers/chat/PresenceController.js`, a plain stateful helper, not a real `ReactiveController`). Keyed **per conversation** (a `Set` of ids; a conversation-less call is attributed to the active conversation and dropped on the next such call or a switch — `handleConversationChange()`), so `chx-message-list` gets `#presence.isTyping()` while a background conversation's typing lights only its sidebar row. Fires `chx-typing-change` (detail `{typing, conversationId}`) when the value actually changes (latched, no re-fire for a repeated call with the same value).
- **`streaming`** — fully automatic, no public method: `chx-chat`'s `#isWaitingForReply()` derives it fresh each render from `#activeDeliveries` (a delivery is in flight) vs. whether `#internalMessages` already has a reply shell for it (`replyToId` match) — true from the instant a send starts until the first chunk lands, `false` once a message exists even while its parts are still `state: "streaming"` (that in-message case is a deliberately different, unimplemented concern, see below).
- `chx-typing-indicator` (text label, `value` prop, default `"Typing…"`, `aria-live="polite"`) and `chx-streaming-indicator` (a decorative dots bubble, `aria-hidden`, styled like an incoming not-own message) are deliberately different shapes — grounded in MUI X Chat's own real `TypingIndicator`/`StreamingIndicator` split (their real source was read, not guessed): presence gets an announced label, "response in flight" gets silent decorative dots because streaming start/finish is already announced by `chx-message-list`'s own `role="status"` region. MUI's in-message "dots inside the streaming bubble" phase (their `StreamingIndicator` mounted *inside* a message) has no equivalent here — would need a per-message/per-part hook, not a list-level slot; not built.

A third, adjacent slot — `initial-loading` — deliberately does **not** follow the "no default content, ever" rule above: it has native `<slot>` fallback content (a default `<md-progress-circular>`), the same opt-in-but-with-a-default shape `chx-attachment`'s own `actions` slot already uses (`<slot name="actions"><md-icon-button>…</md-icon-button></slot>`), not the typing/streaming shape. Gated by `#isInitialLoading()` (`this.loading && this.messages.length === 0`, derived fresh each render from `chx-message-list`'s own existing `.loading`/`.messages` properties — no new property pushed from `chx-chat`, unlike `typing`/`streaming`), so a `loading` pulse for a subsequent scrolled-up "load more" (once real messages already exist) is never mistaken for the initial one, and a genuinely-empty first page correctly stays eligible to show the indicator again on the next auto-triggered page. `md-progress-circular` self-sets `aria-hidden` (purely decorative, same reason as `chx-streaming-indicator`'s dots) — the `Loading messages`/`Messages loaded` announcements live in the same `role="status"` region `#updateStatusText()` already drives for streaming edges. Note there is currently no dedicated "initial load" fetch path to hang this off of at the `chx-chat`/`PaginationController` level — `PaginationController.loadInitial()` exists and is unit-tested but is never actually called from `chx-chat.connectedCallback()`; what fetches the first page in practice is `LoadMoreController.maybeLoad()` auto-firing because a brand-new empty list's `scrollTop` starts at `0`, within its own `LOAD_THRESHOLD`, so it calls the ordinary `loadMore()`. The derived-boolean approach above works correctly regardless of which pagination method performs the fetch, so this slot doesn't depend on that gap being closed — left as a known, separate gap.

A fourth slot, `loading-history`, is `initial-loading`'s complement — the "loading an *older* page" case, with messages already on screen, gated by `#isLoadingHistory()` (`this.loading && this.messages.length > 0`, same derivation shape as `#isInitialLoading()`, mutually exclusive with it by construction since a `loading` pulse can only ever match one of the two). Unlike `typing`/`streaming`/`scroll-to-bottom` above, this one is **rendered by default** — `chx-message-list` imports `chx-loading-history` (`src/components/loading-history/`) itself, same as `chx-message`/`chx-infinity-scroll`, and the slot's own native fallback is a plain `<chx-loading-history></chx-loading-history>`: `<slot name="loading-history"><chx-loading-history></chx-loading-history></slot>`, so an app sees it with zero wiring. An app only ever touches `<chx-loading-history>` directly to *customize* it: slot one in explicitly (`slot="loading-history"`) to set `delay` (ms to wait, once actually visible, before rendering — `connectedCallback()` arms an `IntersectionObserver` that starts/clears the timer as the element intersects/stops intersecting, and `render()` returns `nothing` until the timer fires; a fetch that settles first disconnects the element before the timer ever does, so a fast fetch never flashes it at all) and/or override its own content via its own further `<slot><md-progress-circular></md-progress-circular></slot>` (same opt-in-but-with-a-default shape as the `initial-loading` slot above, nested one level deeper). Unlike `initial-loading` (which nests inside `chx-infinity-scroll`'s own template, replacing it entirely while true), `loading-history` follows `chx-scroll-to-bottom-affordance`'s shape instead: a *sibling* of `chx-infinity-scroll` in `chx-message-list`'s own render(), positioned via its own `:host { position: absolute; inset-inline-start: …; inset-block-end: …; }` (`chx-scroll-to-bottom-affordance`'s own bottom-center-pinned mechanic, here pinned bottom-start instead — logical properties, not `left`/`top`, so it flips correctly under RTL; no message-list.css rule needed for either, both are 100% self-positioned against `chx-message-list`'s own `:host { position: relative }`). Its bubble is `aria-hidden` for the same reason `chx-streaming-indicator`'s dots are — `chx-message-list`'s `#updateStatusText()` sets its `role="status"` text to `Loading messages`/`Loading older messages` directly off the current `#isInitialLoading()`/`#isLoadingHistory()` value each render (no previous-state tracking — `role="status"` only re-announces on an actual text change, and `chx-infinity-scroll`'s own `aria-live="polite"` log covers the arriving messages once loading finishes), as a fully independent, additive branch (the `initial-loading` branch itself is untouched).

### `chx-message` — avatar / meta / content / actions slots

`chx-message` (`src/components/message/message.js`) exposes four slots: `avatar`, the default slot (message content/parts), `meta` (author label, timestamp, etc.), and `actions` (per-message actions like copy/retry). `:host([own])` now also sets `flex-direction: row-reverse` (on top of its existing `align-self: flex-end`) so avatar/body order flips for own messages too. `--chx-message-*` custom properties (`padding`, `border-radius`, `background-color`, `own-background-color`, `avatar-gap`, `meta-gap`, `actions-gap`) are the public theming surface, defaulting to the `--_chx-*` chat tier (see Styling conventions). `:host([compact])` also sets the `--chx-part-*` density tokens (`row-height`, `icon-size`, `gap`, `padding-inline` — text sizes stay on the chat type scale), which inherit through the default slot into every part element — that's how compact reaches the agent components with no JS; don't add a `compact` property to a part for this.

There is **no whole-message render hook** — `chx-chat`/`chx-message-list` had a `messageElement` property (`(message, previousElement?) => HTMLElement`); it's gone. It was a second-class path that skipped everything `#renderMessage` does after building the element — `FocusBehaviorController.ensureSeeded`/`applyToElement` (so a custom row silently dropped out of roving focus, exactly the failure that controller's own doc warns about), the `exportparts` attribute, `partElements` dispatch, and `unread`/`busy`/`aria-label` — which no consumer ever fully replicated. `partElements` is now the only rendering override; the wrapper is always the library's, so every row reliably carries all of the above. Whole-row *appearance* is CSS instead (below), and `chx-message`'s `unread-marker` slot gained `<chx-unread-marker>` as native fallback content (the `initial-loading`/`loading-history` shape, not typing/streaming's) since nothing could slot into it through `chx-chat` anymore.

`#renderMessage` stamps a **closed vocabulary of part names** on each `<chx-message>` host from that row's own state: `message` always, exactly one of `message-own`/`message-incoming`, plus `message-unread`/`message-streaming`/`message-system` where they apply (the last from `parts[0].type === "system"`). `message-incoming` exists only because part selectors can't be negated — there is no `::part(message):not(own)`, so "every row except my own" has to have a name of its own. Closed because `exportparts` has no wildcard — every name a page can target must appear literally in `MESSAGE_STATE_PARTS`/`INFINITY_SCROLL_EXPORTPARTS` (`message-list/parts.js`). Two mechanics these rules depend on: **part selectors don't nest** (no `::part(message-own)::part(message-content)`), so reaching a *particular* row's interior goes through `--chx-message-*` custom properties or plain inherited properties (`color`, `text-align`), which do cross into chx-message's shadow tree; and a page-level `::part()` rule outranks the component's own `:host` rules, so plain declarations land directly. That last point is why `align-self` moved out of `#renderMessage`'s inline `el.style` and into `message.css`'s `:host`/`:host([own])` — an inline style is the one thing `::part(message)` can't beat.

`avatar`/`meta`/`actions` cost zero space when nothing's slotted — via `.message__avatar ::slotted(*) { margin-inline-end: … }` etc., **not** a `:has(::slotted(*))` gate on the wrapper. `:has()` combined with `::slotted()` was tried first and confirmed live, in isolation, to never match in this package's tested Chromium build — not a syntax mistake, an actual unsupported combination right now. `::slotted(*)` alone doesn't need the `:has()` gate at all: it only ever matches when something is genuinely assigned, so the margin naturally costs nothing when the slot is empty.

### `chx-conversations` — the same template-driven shape as the message list

The sidebar (`src/components/conversations/`) went through the identical refactor, for the identical reasons, so read it against "`#renderMessage` — a template, not an element" above.

- **No `buildItem`.** `chx-conversations` had the same whole-row render override `chx-message-list` had, with the same hazard: `#items` selects rows by duck-typing (`typeof el.setTabIndex === "function"`), so a row a consumer built from anything other than a `<chx-conversation-item>` silently dropped out of the roving tabindex. It could go because the two things it was actually used for now have real sources — see below.
- **Rows are a template.** `#renderItems()` returns a keyed `repeat()` over `conversations`; `#itemCache`, its `builderKey` discriminator and the inline sweep are gone, and `#renderedItems` (a snapshot of the previous pass, used for click hit-testing) became a live `querySelectorAll` in `#items`. `#onClick` reads `event.target.closest("chx-conversation-item")` — the event retargets to the row on its way out of the row's shadow root, so a listener inside *this* component's shadow tree sees the row, never what was clicked inside it.
- **The avatar is data-driven.** `ChxConversation.avatarUrl` already existed and was documented as "takes precedence over participant avatars in a conversation list" — it just was not wired. `chx-conversations` now maps `conversation.avatarUrl ?? participants[0]?.avatarUrl` onto the row's new `avatarUrl` property, which the `avatar` slot renders as its **fallback** content, so slotting your own avatar still wins.
- **The row's `typing` slot is filled by the parent, not by a fallback.** `chx-conversation-item` deliberately has no fallback content there (unlike `chx-message`'s `unread-marker`); instead `chx-conversations` puts a `<chx-typing-indicator slot="typing">` into each row from its own template and imports it. That option only exists because rows are a template now — with imperative assembly the choice was "fallback content or a dead feature".
- **Parts** mirror the message vocabulary: `item` on every row, plus `item-active`/`item-unread`/`item-typing`, plus the row's interior exported one hop as `item-avatar`/`item-title`/`item-preview`/`item-badge`. Cheaper than the message case — rows live directly in this component's shadow tree, so the host-level names need no hop at all and the state names need no literal list (nothing has to enumerate them in an `exportparts` string).

### Styling conventions

- CSS files are co-located with their component and imported with `?inline` (`import styles from "./chat.css?inline"`). Vite and the test runner each have a plugin to handle this transform into a Lit `CSSResult`.
- SVG icons (`@material-design-icons/svg`) are imported with `?raw` and rendered via `unsafeSVG()`.
- Theming is three tiers: `--md-sys-*` → `--chx-chat-*` → `--chx-<component>-*`. `src/styles/tokens.css` is adopted first in every rendering component's `styles` and resolves each public `--chx-chat-*` (typography, MD3 color roles, shape, elevation) into a private `--_chx-*` on that host, falling back to `--md-sys-*`. Component tokens and rules read **only** `--_chx-*`, never `--md-sys-*` directly. **Never declare a `--chx-chat-*` in any component, `chx-chat` included** — a declaration on a nested host would hide the value a consumer set on an ancestor; declaring only the private resolver on every host keeps ancestor overrides and standalone defaults both working. `tokens.css` also bridges `--md-sys-typescale-*-font` (only the `*-font` roles — bridging a size or color would create a cycle with the resolver) so `md-*` children follow `--chx-chat-font-family`. Message and composer text share `--_chx-body-large-font-size`/`-line-height` (1rem/1.5rem), dropping to body-medium in compact; agent rows and other UI text use body-medium.
- Custom elements are registered with the `@customElement` Lit decorator (using the 2023-11 decorator spec, transformed by Babel in both build and test).
- **`::part()` only forwards one shadow level.** A page-level (or even a grandparent component's) `::part()` rule cannot reach an element nested two-or-more shadow roots deep — e.g. `<chx-message>`, which lives inside `chx-infinity-scroll`'s shadow root, itself inside `chx-message-list`'s — without an `exportparts` chain at *every* intermediate host. Confirmed live: a page-level `chx-message::part(actions)` rule silently matches nothing at that depth. **The same is true for a CSS custom property set via a selector**, not `element.style.setProperty()` — a page-level `chx-message { --chx-message-background-color: … }` rule doesn't reach that deep either, for the same "a rule is scoped to the tree it's defined in" reason; only the initial assumption that custom properties are somehow exempt from this was wrong. `chx-message-list` now maintains that chain (`MESSAGE_EXPORTPARTS` on each `chx-message`, `INFINITY_SCROLL_EXPORTPARTS` on the `chx-infinity-scroll` it renders), which is what makes `chx-message-list::part(message-content)` work from a page — see the `chx-message` section above, and `chat.stories.js`'s `Dividers` and `agent.stories.js`'s `messageStyleOverrides` for worked examples. A custom property set inside a *matching* `::part()` rule does inherit into that part's shadow tree; the original "doesn't reach that deep" case was a selector that never matched in the first place, not an inheritance limit.

### Build output

Vite builds with `preserveModules: true` — each source file maps 1-to-1 to a `dist/` file. Two JS entries, `src/index.js` (`.`) and `src/agent.js` (`./agent`), plus `src/styles/tokens.css` copied verbatim to `dist/tokens.css` (`./tokens.css`) by a small `closeBundle` plugin in `vite.config.mjs`. `rollupOptions.preserveEntrySignatures: "strict"` is load-bearing: Vite's app-mode build defaults it to `false`, which silently strips every entry's `export`s (dist/index.js became bare side-effect imports). `lit` and all `@symblight/wc-material` subpaths are external. `vite-plugin-dts` generates `.d.ts` files and prepends a `/// <reference path="...elements.d.ts" />` triple-slash reference to each output file. `src/elements.d.ts` extends `HTMLElementTagNameMap` with the registered tag names.

### Code comments

Keep JSDoc and comments minimal. A custom element's class-level JSDoc is just `@tag`/`@summary`, one
short line each (see any component under `src/components/`) — no prose paragraphs, no `@param`/
`@returns` walkthroughs above every method, no restating what the code already says. Comment only what
isn't obvious from reading the code itself (a non-obvious constraint, a workaround, a gotcha).
